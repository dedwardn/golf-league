# S15d2 Set up the bay

**Implemented**

- A season carries its bay settings: an ordered list of lines, each a Trackman menu, a setting and its value. They are stored on the season's row and written through `create_season` until S17. No rule reads them.
- `bay_round` builds the Set up the bay screen for one open round of a team season. The screen shows the round's format and tee, the Game menu's lines, and each other menu in first-written order. A round that is closed, a draft or unknown gives None, and so does any round of an individual season.
- `/rounds/{number}/bay` shows the screen to any player with a link. Without a cookie the request is refused, and a round with no bay is a 404. Home links to the bay from each open round of a team season.
- T3 carries the owner's settings, so the demo season reads as the league will.

**Proposal for S16: making room in `results.py`**

`results.py` is at 293 of 300 lines, and S16's round page will need views of its own. I propose that S16 starts with a commit that only moves code, as S15b did when it moved the team branch into `team_rounds.py`:

- `HomePlayer`, `HomeTeam`, `HomeRound` and `HomeView` move into `domain/home.py`, the module that builds them. `home.py` grows from 93 to about 150 lines.
- `BayMenu` and `BayRound` move into `domain/bay.py`. It grows from 47 to about 70 lines.
- `results.py` keeps what the rules and `compute_season` produce, and drops to about 210 lines.
- S16's round page views are then born in the round page's own module.

The rule then reads: a screen module owns the views it builds, and `results.py` owns rule output. Imports keep their direction: `web` already imports domain types for display, and `services/play.py` already imports `home.py`. The edits are the `results.py`, `home.py` and `bay.py` rows of ARCHITECTURE's module map, plus one line under Conventions.

The alternative is one `domain/views.py` for every screen's dataclasses. It keeps the dataclasses apart from the functions that build them, but it would itself fill up as S16 and S17 add screens. That decision belongs to S16's plan and the architect.

**Audit**

The reviewer made 8 findings and read the code without running it. The architect ruled on each.

1. **A bay setting that clashes with a fixed block.** Examples: a "Players" menu, a Game line named "Holes", or a menu written "game". No code change, since SPEC states no bound on a menu's name. Parked as an open question for S17 in BUILD_PLAN, where the architect leans towards no check.
2. **A player outside the season reads the bay.** No code change. R12 hides results and other players' cards, and the bay screen holds neither. SPEC section 7 now says so, in a sentence that states what the plan approved and a test pins.
3. **The format assert and the round lookup are repeated in `bay.py`, `home.py` and `play.py`.** Declined. The lookups differ: `bay.py` also filters on `closed_at`, and `home.py` builds a dict. A helper for two or three lines would move code without reducing it.
4. **The Game filter is written twice in `bay.py`.** Declined. Grouping every menu and then popping Game swaps one comparison for a `pop` and a conversion, and `bay_round` would grow.
5. **`SeasonFacts.bay_settings` defaults to `()`.** Declined. A field whose empty value is a real state of the season gets that value as its default, as `late_until`, `format`, `team_cards` and `mode` do. S9B is such a season.
6. **Format fields are read by position.** Accepted. Each entry in `formats.html` is now a mapping with `name`, `line` and `game_type`, read by key in `home.html` and `bay.html`. The tests are unchanged.
7. **The web layer repeats the domain's None cases.** Accepted. The 404 test keeps only the closed round, since the route's one branch is `bay is None`. The domain tests cover each None condition, and the services test covers the draft round.
8. **The step report names a temporary path.** Accepted. The Click-through bullet now says how to rebuild the database.
