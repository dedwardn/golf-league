# S1 Strokes

**Implemented**

An index and a tee now turn into strokes on holes. `playing_handicap` applies R1
exactly over integers, `allocate_strokes` spreads the result across 18 holes by
stroke index per R2, and `net_card` subtracts them hole by hole per R3, with
`stableford_points` scoring the result against par. `Tee` and `Card` carry the
R13 shape checks. 21 tests, every worked example in R1, R2 and R3 covered.

**Public API**

```python
# facts.py
@dataclass(frozen=True)
class Tee:
    pars: tuple[int, ...]
    stroke_indexes: tuple[int, ...]
    course_rating_tenths: int
    slope: int
    @property
    def par_total(self) -> int

@dataclass(frozen=True)
class Card:
    scores: tuple[int, ...]

# results.py
@dataclass(frozen=True)
class NetCard:
    scores: tuple[int, ...]
    @property
    def total(self) -> int

# strokes.py
def playing_handicap(index_tenths: int, tee: Tee, allowance: int) -> int
def allocate_strokes(playing_handicap: int, tee: Tee) -> tuple[int, ...]
def net_card(card: Card, tee: Tee, playing_handicap: int) -> NetCard
def stableford_points(net: NetCard, tee: Tee) -> tuple[int, ...]
```

Both dataclasses and `allocate_strokes` raise `ValueError` on impossible input.

*2. The shadowed parameter stays. Settled.*

In `strokes.py` the parameter `playing_handicap` on `allocate_strokes` and
`net_card` shadows the module-level function of that name. The owner weighed
having `net_card` take the allocated strokes instead, which is closer to R3's
wording and would remove the shadow, and rejected it as redesigning a green step
over a nit: `net_card(card, tee, playing_handicap)` reads correctly at the call
site, which is worth more than a collision no current code can trip over.

The rule, so it does not cascade: if a function ever needs both the value and the
function, rename the parameter inside that function, never the public function.
The glossary owns the public name.

*3. Float safety under R1, settled once so it need not be re-derived.*

Before the R1 tests were written, a sweep looked for any input where exact
`Fraction` arithmetic and naive float arithmetic give a different playing
handicap. Ranges covered, all with half-up rounding as `floor(x + 0.5)`:

| Sweep | Index | Slope | Course rating | Par total | Allowance |
|---|---|---|---|---|---|
| 1 | 0.1 to 39.9 in tenths | 113 | 6 values, 69.7 to 74.4 | 70, 71, 72 | 100 |
| 2 | 0.1 to 54.4 in tenths | 113, 117, 120, 125, 131, 140, 155 | 9 values, 68.5 to 75.6 | 70, 71, 72 | 100, 95, 90, 85, 80, 75, 50 |
| 3 | 0.1 to 54.4 in tenths | 113 | 6 values, 69.7 to 74.4 | 70, 71, 72 | 100 |
| 4 | 11.3, 22.6, 33.9, 45.2 | every slope 100 to 155 | 10 values, 68.0 to 76.1 | 70, 71, 72 | 100, 95, 90, 85, 80, 75, 70, 60, 50 |

Sweep 3 isolated the 987 inputs whose exact result lands on a half boundary.
Sweep 4 used indexes whose tenths are a multiple of 113, so that exact halves are
reachable on slopes other than 113.

**Result: zero divergences across all four sweeps.** No input was found where
floats give a wrong playing handicap.

Why: `x + 0.5` itself re-rounds to nearest, and at the magnitude of a playing
handicap the accumulated error stays below half an ulp of the result, so the
addition repairs the error it would otherwise expose.

**This is a property of the arithmetic, not of the league rules, and it is not a
law.** It depends on the result being a small number. Do not carry the conclusion
forward to R4, R5 or R7 without re-deriving it for those magnitudes. Equally, do
not write float-divergence tests at those rules: a test suite pins behaviour the
league relies on, and float behaviour is not that.

`Fraction` is used throughout regardless, so the question does not have to be
asked again rule by rule.

The R1 test that does exist pins the real hazard, which is Python's `round`
sending an exact half to even: index 4.5 on a slope-113 tee whose rating equals
par gives an exact 4.5, which must round up to 5 where `round` gives 4.
