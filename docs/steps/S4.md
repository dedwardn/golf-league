# S4 Duel contests

**Implemented**

One duel contest now turns its config, its pairings and the round's net entries into
awards. Each pairing's two sides are built from on-time entries, a side that is missing
or absent is replaced by a virtual side that excludes the players it meets, the two are
compared under R8, and every player on a side collects that side's win, draw or loss
points times the multiplier. Late cards are then swept up one at a time: a late card
from a player who earned nothing meets the virtual side alone (R9).

**Public API**

```python
# facts.py
Basis = Literal["holes", "total", "stableford"]

@dataclass(frozen=True)
class Pairing:
    a: tuple[str, ...]
    b: tuple[str, ...] = ()

@dataclass(frozen=True)
class ContestConfig:
    key: str
    basis: Basis
    points_win: Fraction
    points_draw: Fraction
    points_loss: Fraction
    side: Literal["single", "bestball"]
    multiplier: int = 1
    virtual_n: int = 4

# results.py
Reason = Literal["win", "draw", "loss"]

@dataclass(frozen=True)
class Award:
    player_id: str
    contest_key: str
    points: Fraction
    reason: Reason

# contests.py
def duel_awards(
    entries: Sequence[NetEntry],
    tee: Tee,
    closed_at: datetime | None,
    pairings: Sequence[Pairing],
    config: ContestConfig,
) -> tuple[Award, ...]
```

Every field is read by this step. `closed_at` is `None` while the round is open, when
no card is late, which is the glossary's on-time card rather than an extra case.

Awards come back in pairing order, side `a`'s players before side `b`'s, late cards
last. A virtual side has no players, so the same award path gives it nothing and needs
no test for who a virtual side pays.

**Deviations from plan**

1. `duel_awards` has no `references` parameter. The approved signature had six
   arguments and `pyproject.toml` sets `max-args = 5`, which cannot be widened to pass
   the gate. The virtual side is built from this round's on-time entries, which is
   R7's default reference round and the only reference this step can resolve: it was
   for that same reason that `reference_rounds` is not yet a `ContestConfig` field.
   S9 adds the parameter and the field together, in the step that resolves them. The
   owner was told before this report and has not ruled on it.
2. Two test names are shorter than planned: `test_r9_virtual_n_is_one_or_more` and
   `test_r9_a_pairing_has_at_least_one_side` cite the message each check raises.
3. The `a_config` helper lives in `test_contests.py`, not `conftest.py`. It has one
   caller: `test_facts.py` builds a `ContestConfig` directly, because the field it
   tests is the one the helper would hide.

Nothing else differs. The eight planned files are the eight files changed, and the
dataclass fields are the eight the owner listed.

Applied at audit:

4. The late sweep no longer checks a set of players who already earned. Every award
   from the pairings comes from a side built out of on-time entries, and R13 gives a
   player one counted card per round, so a player with a late card can never be in
   that set. R9's "got no points in this contest" is automatic, and a comment now says
   why rather than the code asking twice.
5. `_outcome_awards` takes the two sides and calls `compare` itself, instead of taking
   a `Comparison` both callers built the same way. It also makes `result.winner is a`
   true by construction: the comparison is now made of the objects it is compared
   against, so a change to `compare` cannot silently invert every award.
6. `side` has no default. R9 gives defaults to `allowance`, `multiplier` and
   `virtual_n` only, and a duel config that forgets to name its side should not quietly
   become single.
7. `Reason` is an alias in `results.py` beside `Award`, imported by `contests.py`,
   which restated the three outcomes in its own `Literal`. One home for the vocabulary,
   as `Basis` sits with the field that uses it.
8. The comment above the `virtual_n` check is gone. R9 states the bound now, so the
   check has a rule to point at and needs no narration of what a bad value would do.
9. `assert awards[0].contest_key == "duel"` is deleted: the tuple equality above it
   already pinned that field, so it could not fail. Vulture then reported
   `contest_key` as unused, which was true, so the draw test asserts it where that
   test checks fields rather than whole objects and the assertion can fail.
10. `_declared_side` raises `ValueError` when `side` is single and a pairing side names
    more than one player. R9 states it, and with `side`'s default gone this is the
    combination most likely to be misconfigured. It was the owner's ruling from the
    previous review, outstanding until now.

Rejected at audit, on the owner's ruling:

11. The `virtual_n` bound and `Pairing`'s check stay. Both were reported as error paths
    no rule asked for, and the diagnosis was right about the state of the docs, not
    about the checks: a bad value reaches a facts dataclass from an admin form at S14,
    not from `src`, so no caller in `src` is expected yet. R9 and `docs/ARCHITECTURE.md`
    now state the bounds the code enforces.
12. `_side_awards` is not inlined into `_outcome_awards`' three branches. That would put
    the award construction in six places to remove one repeated annotation; the alias
    in item 7 removes the annotation instead.

**Deliberately not done**

- `allowance` and `reference_rounds` on `ContestConfig`, resolving reference rounds,
  and R7's rule that a reference round must use this round's tee. S9.
- `kind` on `ContestConfig`. It becomes a discriminator when S5 dispatches on it.
- Field, allplay and teambonus contests, and manual awards. S5 and S6.
- A round id on `Award`. The round is the caller's context, as it is for every other
  result here; S9 groups awards by round.
- Checking that a `single` contest's pairing sides name one player each. That needs the
  config, so it is not a shape check on `Pairing`, and no rule asks for it.

**Open questions**

1. The `references` parameter, if you want it back at S4 rather than S9. Keeping it
   means finding a fifth argument to drop, and the candidates are all read: `entries`,
   `tee`, `closed_at`, `pairings`, `config`. S9 will meet the same wall when it adds
   references, so the shape that survives may be a round-shaped argument rather than
   five loose ones. Worth settling when S9 is planned.
2. `Award.reason` names the outcome, not the circumstance, so a late card's award is
   `"win"` like any other. The round page at S16 may want to mark it as late; that
   needs a field this step has no reader for.
