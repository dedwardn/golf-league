# S6 Teambonus and manual awards

**Implemented**

A teambonus contest now reads the awards another contest of the same round produced,
sums them per season team over on-time cards only, and pays `bonus` to every on-time
member of the top team, shared equally when teams are level. Manual awards become awards
as the admin entered them, with no multiplier. Before either, `test_contests.py` was
split into one file per contest kind, in its own commit.

**Public API**

```python
# facts.py
@dataclass(frozen=True)
class TeamBonusConfig:
    key: str
    source: str
    bonus: Fraction
    multiplier: int = 1

@dataclass(frozen=True)
class ManualAward:
    player_id: str
    key: str
    points: Fraction

# results.py
Reason = DuelReason | Literal["position", "record", "bonus", "manual"]

@dataclass(frozen=True)
class Award:
    player_id: str
    key: str  # was contest_key
    points: Fraction
    reason: Reason

# contests.py
def teambonus_awards(
    entries: Sequence[NetEntry],
    closed_at: datetime | None,
    round_awards: Sequence[Award],
    teams: Mapping[str, str],
    config: TeamBonusConfig,
) -> tuple[Award, ...]

def manual_awards(manual: Sequence[ManualAward]) -> tuple[Award, ...]
```

`teambonus_awards` takes no `tee`: nothing here is netted or compared, and it is the one
contest kind that reads awards instead of cards. It selects `config.source` from
`round_awards` itself rather than being handed a pre-filtered list, so the field is read
where R9 names it. Awards come back in entry order.

`share` is `bonus * multiplier / len(top)`, a `Fraction` over an `int`, so three level
teams take an exact third each (D14).

**Deviations from plan**

1. The plan had me edit the `award` row of the glossary in `docs/SPEC.md` to record the
   two new reason names. The owner removed that instruction mid-step, because it put a
   `docs/` edit in my hands against CLAUDE.md rule 4, and made the edit themselves in
   commit `520aadb`. I made no `docs/` edit until this report.
2. `ManualAward.key` was planned as "unique in the round like a contest key". It is
   documented as a label instead: an adjustment given to two players in one round shares
   one key, and the planned wording would have become a validation at S11 or S14 that
   forbade something legitimate. The owner caught this.
3. Four tests beyond the seven planned, all from answers given during the step:
   `..._three_teams_level_at_the_top_get_a_third_each` and
   `..._a_team_with_no_on_time_card_does_not_enter_the_ranking` pin the rulings on
   questions 2 and 3; `..._with_no_team_among_the_on_time_cards_gives_nothing` covers the
   empty path; and `..._two_teams_that_played_and_earned_nothing_share_the_bonus` was
   asked for by the owner. The planned `..._teams_level_at_the_top_share_the_bonus`
   became the two-team and three-team cases.
4. `..._keeps_negative_points` became
   `test_r9_a_manual_award_takes_points_away_and_its_key_is_a_label`, asserting the
   shared key as well, which deviation 2 made worth pinning.

Nothing else differs. The planned files are the files changed.

Applied at audit:

5. `Award.contest_key` is `Award.key`. `manual_awards` puts the admin's label in it, so
   the old name was false for one of the four reasons, while every fact type already
   calls the field `key` and the glossary already said an award comes from a contest
   "or by the admin". Three call sites. `docs/steps/S4.md` still shows the old name and
   is left alone: a step report records what that step did.
6. The module docstring loses the two lines describing teambonus and manual awards. Both
   function docstrings say it, and `facts.py` says it a third time.
7. The `duel_award` test fixture no longer picks a reason from the points. Nothing reads
   `Award.reason` here, so the branch could not change an outcome.
8. The two-team and three-team share tests assert the whole tuple rather than the points
   alone. They are the two tests where who receives the share matters as much as the
   amount, and neither would have failed if the bonus went to the wrong players.

Settled at audit, no code change, landing in the owner's next docs commit:

9. R9 does not say what makes a team enter the teambonus ranking. The sentence says
   "card", not "award", so the code's reading is the only one it supports, but a clause
   is being added: a team that played and holds no award in the source still has a sum of
   zero and enters. After S6b the two readings select the same teams in any season the
   pipeline can produce, since every on-time duel player will earn something, so the
   clause is there for the function's contract, not for a season case.
10. Season teams arrive as `Mapping[str, str]`, which reads against ARCHITECTURE's "No
    dicts as records". That convention was aimed at a dict standing in for a dataclass.
    Player to team is a lookup, not a record, so the convention gains a clause saying so
    and the `facts.py` row names season teams, which `SeasonFacts` carries from S9.

**Open questions**

1. `test_r9_teambonus_two_teams_that_played_and_earned_nothing_share_the_bonus` rests on
   a player who has an on-time card and no award in the source contest. S6b removes that
   shape from anything the pipeline can produce, since every on-time player will then
   earn from a pairing or from the virtual side. The test keeps its place as a contract
   guard on `teambonus_awards`, which takes `round_awards` as an argument, and it is
   still the only test that fails if the ranking is filtered on holding an award rather
   than on having played. Its comment stops being true and is rewritten in S6b.
2. A teambonus whose `source` names another teambonus would sum a bonus into a bonus.
   R9 says `source` names a duel contest; nothing here can check it, and S9 can.
3. An award does not say which team earned a teambonus bonus, so a round page can show
   only "bonus". The field belongs to the step that reads it, S13 or S16.
