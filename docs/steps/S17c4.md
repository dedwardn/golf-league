# S17c4 Bay settings by menu

**Implemented**

- Season setup's bay settings card, on the create form and on the read-back, reads one section per menu, Game first and then the others as first written, which is the bay screen's order. Each section is headed by its name.
- A line with a name reads it as text, with × at its right and its value below in a full-width box that wraps (`field-sizing: content`). A line or section without a name reads a box. Under this stateless rule, a typed name reads as text once the card is redrawn.
- Each section ends with Add a setting, and Add a menu follows the last section. Each redraws the card and stores nothing, as × and Enter do. The create form starts with one unnamed menu and one empty line.
- Lines are stored as before, as menu, setting and value, in section order, each field trimmed. A line with no setting and no value is dropped. There is no migration, and `bay.html` is unchanged.
- `docs/design/admin-season.html`'s bay card is redrawn by menu from the built template (the owner, at the plan).

**Public API**

- `league.domain.bay.bay_menus(settings: Sequence[BaySetting]) -> tuple[BayMenu, ...]`
- `league.web.bay_form.typed_menus(form: FormData) -> tuple[BayMenu, ...]`
- `league.web.bay_form.pressed_menus(form: FormData, menus: tuple[BayMenu, ...]) -> tuple[BayMenu, ...] | None`
- `league.web.bay_form.typed_settings(menus: Sequence[BayMenu]) -> tuple[BaySetting, ...]`
- `league.web.bay_form.NEW_MENU: BayMenu`

**Deviations from plan**

- **Docstrings say "a line's Remove", not "a line's ×".** Ruff's RUF002 refuses the multiplication sign in a docstring. The button's aria-label reads "Remove {setting}".
- No other deviation.

**Deliberately not done**

- Trackman's exact menu and setting names, and values as selects, stay parked until the owner's photos.
- Renaming or reordering a stored line or menu in place is not done: × and Add a setting cover a rename.
- `bay.html`, the store and the services are unchanged.

**The audit**

The reviewer raised six findings, and the architect ruled on them:
- **1, declined.** The form-list reader stays private in both `bay_form.py` and `admin_season.py`, as the plan review ruled. Either fix would make a generic form reader a public name of the bay card's module or move lines rather than remove them.
- **2, applied.** `bay_form.py` imports `FormData` from `fastapi.datastructures`, since `fastapi` is the declared dependency.
- **3, applied.** The D18 save test types a value with spaces at both ends and a line break inside, and asserts it is stored trimmed with the break kept. BUILD_PLAN's S17c4 Accept says so.
- **4, applied.** `_added` and `_removed` are inlined into `pressed_menus`, which builds the changed section and does one splice. The menu name carried on each typed line as well as on its section stays, since the plan chose `BayMenu` as the form's shape.
- **5a, sent to the owner.** A line typed under an unnamed menu is stored with an empty menu, as written (S17c1's rule), and the bay screen then shows a block with no heading. See the open question.
- **5b, declined.** A section emptied by × stays drawn until the next read-back and stores nothing, as the plan review's ruling 3 settled.
- **6, applied.** The template macro is `bay_card`, so it no longer shares `bay_menus`'s name.

**The owner's click-through**

On the phone, checks 1 to 6 were OK: the read-back by menu with every name in full and Mulligans wrapped, Add a setting, × on Mulligans, Add a menu saved as a new section, Enter in a value box starting a new line, and the bay screen unchanged. On the open question (the audit's finding 5a) the owner chose (A): an empty menu name, setting name or value box reads the hint "Menu", "Setting" or "Value" (`placeholder`), so a menu left unnamed shows on the form, and a line under it is still stored as written. The empty-form test asserts the three hints, BUILD_PLAN's S17c4 text says so, and the design file's value boxes carry the hint as the template's do.
